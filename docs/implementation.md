# 구현 가이드

이번 단계는 직접 호출 말고 결과를 이벤트로 넘길 수 있다는 사고를 익히는 실습입니다.
starter 브랜치에서는 세부 구현보다 각 파일이 맡는 책임과 확인 기준을 먼저 봅니다.

## 1. 구현 전에 확인할 문제

주문 생성 뒤 알림 같은 후속 작업을 바로 호출하면 주문 흐름이 알림 흐름을 직접 알게 됩니다.
이벤트 발행과 소비를 나누면 주문 생성 쪽은 결과를 알리고, 알림 쪽은 그 결과를 받아 별도 흐름으로 처리할 수 있습니다.

## 2. 구현 순서

1. 이벤트 DTO에 담을 최소 정보를 정합니다.
2. 주문 생성 흐름에서 이벤트를 만들고 발행합니다.
3. 소비자가 이벤트를 받아 알림 흐름으로 연결합니다.
4. 주문 API와 알림 조회 API로 흐름을 실행합니다.
5. 직접 호출과 이벤트 전달의 차이를 말로 비교합니다.

## 3. Step 1. 이벤트 DTO 만들기

### 해야 할 일

`OrderCreatedEvent`에 주문 생성 결과를 설명하는 최소 필드를 둡니다.
후속 알림 흐름에 필요한 정보만 담고, 처리 로직은 이벤트 안에 넣지 않습니다.

### 왜 이 작업을 하는가

이벤트는 "무슨 일이 일어났는가"를 전달하는 메시지입니다.
필드가 너무 많으면 발행자와 소비자가 다시 강하게 묶일 수 있습니다.

### 확인 방법

주문 id, 사용자 id, 상품명, 메시지처럼 알림 흐름이 이해할 수 있는 정보만 담겼는지 확인합니다.

## 4. Step 2. 이벤트 발행 연결

### 해야 할 일

주문 생성이 끝난 뒤 이벤트를 만들고 발행 서비스로 넘깁니다.
발행 서비스는 이벤트를 브로커로 보내는 역할에 집중합니다.

### 왜 이 작업을 하는가

주문 서비스가 알림 처리까지 직접 맡지 않게 하기 위해서입니다.
주문 흐름은 주문 생성 결과를 알리고, 후속 처리는 소비자가 담당합니다.

### 확인 방법

주문 생성 요청 뒤 이벤트 발행 흐름이 호출되는지 확인합니다.

## 5. Step 3. 이벤트 소비 연결

### 해야 할 일

소비자는 큐에서 이벤트를 받고 알림 기록 흐름으로 넘깁니다.
이번 실습에서는 후속 작업을 알림 기록 정도로 최소화합니다.

### 왜 이 작업을 하는가

소비자를 분리하면 주문 생성과 알림 처리를 같은 메서드 안에서 강하게 묶지 않아도 됩니다.

### 확인 방법

`POST /event-orders`로 주문을 만든 뒤 `GET /event-orders/notifications`에서 알림 기록을 확인합니다.

## 6. Step 4. 직접 호출과 비교

### 해야 할 일

동기 호출이었다면 어느 코드가 알림 서비스를 직접 알아야 했는지 설명합니다.
이벤트 방식에서는 어떤 책임이 큐 뒤로 이동했는지 비교합니다.

### 왜 이 작업을 하는가

이벤트 기반 구조는 도구 사용법보다 책임 분리와 결합도 완화의 이유를 이해하는 것이 중요합니다.

### 확인 방법

`주문 생성 -> 이벤트 큐 -> 알림 처리` 그림을 말로 설명합니다.

## 마지막 확인

```bash
docker compose up -d
./gradlew test
./gradlew bootRun
```

그 다음 아래 흐름을 실행합니다.

1. `POST /event-orders`
2. `GET /event-orders/notifications`
