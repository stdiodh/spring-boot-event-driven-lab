# 체크리스트

## 1. 기능 확인

- [ ] `./gradlew test`가 통과합니다.
- [ ] `POST /event-orders`로 주문 생성 흐름을 실행합니다.
- [ ] `GET /event-orders/notifications`로 알림 소비 결과를 확인합니다.
- [ ] RabbitMQ 실행이 필요한 흐름과 테스트만으로 확인되는 흐름을 구분합니다.

## 2. 코드 구조 확인

- [ ] `OrderCreatedEvent`는 후속 작업에 필요한 최소 정보를 담습니다.
- [ ] `EventPublisherService`는 이벤트 발행 책임에 집중합니다.
- [ ] `NotificationConsumer`는 이벤트를 받아 알림 기록 흐름으로 넘깁니다.
- [ ] `OrderService`는 알림 세부 처리까지 직접 맡지 않습니다.

## 3. 실패 케이스 확인

- [ ] 메시지 큐가 내려가면 이벤트 전달 흐름이 실패할 수 있음을 설명합니다.
- [ ] 중복 소비와 재처리 문제는 이번 시퀀스에서 다루지 않는다는 점을 설명합니다.
- [ ] 이벤트 기반 구조가 항상 정답은 아니라는 점을 설명합니다.

## 4. 설명할 수 있어야 하는 것

- [ ] 동기 호출과 이벤트 전달 차이
- [ ] 발행자와 소비자의 역할 차이
- [ ] 메시지 큐가 중간에 있는 이유
- [ ] MSA 관점에서 이벤트가 이동하는 그림

## 5. 남은 한계와 다음 시퀀스 연결

이번 구현은 이벤트 기반 사고를 익히기 위한 입문 예시입니다.
운영 환경의 재처리, 중복 소비, 장애 복구, 분산 트랜잭션은 별도 주제로 남깁니다.
