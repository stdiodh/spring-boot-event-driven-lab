# 이론 정리

## 1. 왜 이 개념이 필요한가

서비스가 커지면 한 작업이 끝난 뒤 여러 후속 작업이 이어지는 경우가 많아집니다.
주문 생성 뒤 알림, 로그, 분석 이벤트를 모두 직접 호출하면 주문 서비스가 많은 책임을 알게 됩니다.

이벤트 기반 흐름은 어떤 일이 일어났다는 사실을 발행하고, 다른 쪽이 그 이벤트를 소비하도록 분리하는 선택지입니다.

## 2. 기존 방식의 한계

직접 호출은 단순하고 추적하기 쉽습니다.
하지만 후속 작업이 늘어나면 주문 서비스가 알림 서비스, 로그 서비스, 분석 서비스의 호출 방식까지 알게 될 수 있습니다.

서비스를 나눠 운영한다고 가정하면 이런 직접 의존은 배포와 장애 영향 범위를 더 복잡하게 만듭니다.

## 3. 이번 시퀀스에서 선택한 접근

- 주문 생성 결과를 `OrderCreatedEvent`로 표현합니다.
- `EventPublisherService`는 이벤트를 브로커로 전달합니다.
- `NotificationConsumer`는 이벤트를 받아 알림 기록을 남깁니다.
- 메시지 큐는 발행자와 소비자를 느슨하게 연결하는 전달 장치로 봅니다.

## 4. 핵심 개념

### 동기 호출

요청한 쪽이 상대 작업이 끝날 때까지 기다리는 방식입니다.
흐름은 단순하지만 호출 대상이 늘어날수록 결합이 강해질 수 있습니다.

### 이벤트

어떤 일이 일어났다는 사실을 담은 메시지입니다.
이번 예시에서는 주문 생성 결과를 후속 알림 흐름으로 넘깁니다.

### 메시지 큐

발행된 메시지를 전달하고 소비할 수 있게 도와주는 중간 장치입니다.
발행자와 소비자가 직접 서로를 알지 않아도 흐름을 이어줄 수 있습니다.

### MSA 관점

서비스가 나뉘면 한 서비스의 결과를 다른 서비스가 알아야 하는 장면이 많아집니다.
이벤트와 메시지 큐는 직접 호출을 줄이는 선택지 중 하나입니다.

## 5. 짧은 예제와 해설

```kotlin
data class OrderCreatedEvent(
    val orderId: Long,
    val userId: String,
    val productName: String,
    val message: String
)
```

이벤트에는 후속 알림 흐름이 이해할 수 있는 최소 정보만 담습니다.
주문 생성 후 어떤 일이 일어났는지를 전달할 뿐, 알림 처리 방식을 이벤트 안에 넣지 않습니다.

```kotlin
fun publishOrderCreated(event: OrderCreatedEvent) {
    rabbitTemplate.convertAndSend(exchangeName, routingKey, event)
}
```

발행자는 이벤트를 브로커로 넘기는 책임만 맡습니다.
소비자는 그 이벤트를 받아 알림 기록 같은 후속 작업을 수행합니다.

## 6. 다음 구현으로 연결되는 지점

이 시퀀스는 운영용 이벤트 시스템 전체를 다루지 않습니다.
메시지 재처리, 중복 소비, 장애 복구, 분산 트랜잭션은 이후 확장 주제로 남기고, 이번에는 책임 분리와 흐름 이해에 집중합니다.

- MSA 전체 구현보다 `주문 생성 -> 이벤트 큐 -> 알림 처리` 흐름을 말로 설명하게 합니다.
