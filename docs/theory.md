# 이벤트 기반 사고 확장

> 요청/응답 중심 구조 밖에서 이벤트가 왜 필요한지, 그리고 메시지 큐가 어떤 문제를 완화하는지 이해하는 문서입니다.

> 이번 시퀀스 한 줄 요약  
> 이번 실습은 `주문 생성 -> 이벤트 발행 -> 알림 소비` 예시 하나로, 직접 호출과 이벤트 전달의 차이를 가볍게 체험하는 과정입니다.

## 먼저 이것만 기억해도 됩니다

- 동기 호출은 바로 결과를 기다리고, 비동기 전달은 결과를 다른 흐름으로 넘길 수 있습니다.
- 이벤트는 “어떤 일이 일어났다”는 사실을 다른 쪽에 알려주는 방식입니다.
- 메시지 큐는 발행자와 소비자를 느슨하게 연결해줍니다.
- MSA에서는 서비스가 따로 있고, 이런 이벤트가 큐를 통해 이동하는 그림을 자주 보게 됩니다.

## 이 주제를 왜 배우는가

처음에는 서비스끼리 직접 호출해도 충분합니다.  
하지만 기능이 커지고 후속 작업이 늘어나면 “이 작업이 끝나면 저 작업도 해야 해”라는 연결이 점점 많아집니다.

예를 들어 주문이 생성되면 알림도 보내고, 로그도 남기고, 분석 이벤트도 쌓고 싶어질 수 있습니다.  
이때 모든 후속 동작을 주문 서비스가 직접 호출하기 시작하면 한 서비스가 너무 많은 책임을 가지게 됩니다.

그래서 이번 실습에서는 결과를 이벤트로 발행하고, 다른 쪽이 그 이벤트를 소비하는 최소 구조를 봅니다.  
목표는 Kafka 운영 전문가가 되는 것이 아니라, “아 이런 흐름도 있구나”를 선명하게 잡는 것입니다.

## 이번 실습 흐름을 먼저 한눈에 보기

1. 사용자가 주문 생성 요청을 보냅니다.
2. `OrderService`가 주문 생성 결과를 `OrderCreatedEvent`로 만듭니다.
3. `EventPublisherService`가 RabbitMQ로 이벤트를 보냅니다.
4. `NotificationConsumer`가 이벤트를 받아 알림 기록을 남깁니다.
5. 알림 조회 API로 후속 동작이 분리되었는지 확인합니다.

짧게 말하면 이번 실습은  
**주문 생성 → 이벤트 발행 → 알림 소비 → 흐름 비교**를 익히는 과정입니다.

> 한 줄로 다시 보기  
> “결과를 직접 호출로 이어갈까, 이벤트로 넘길까?”를 비교해보는 실습입니다.

## 오늘 꼭 잡아야 할 질문

- 왜 주문 서비스가 알림 서비스까지 직접 호출하지 않을까요?
- 이벤트는 어떤 데이터를 담아야 할까요?
- 메시지 큐가 있으면 발행자와 소비자가 어떤 점에서 덜 묶일까요?
- MSA는 왜 무조건 답이 아니라고 하나요?

## 중요한 코드 먼저 보기

### 1. 이벤트 DTO

```kotlin
data class OrderCreatedEvent(
    val orderId: Long,
    val userId: String,
    val productName: String,
    val message: String
)
```

- 이 객체는 “주문이 생성되었다”는 결과를 다른 쪽으로 넘기는 최소 정보만 담습니다.
- 학생이 기억해야 할 핵심은 **“이벤트는 사실을 전달하는 작은 메시지”**라는 점입니다.

### 2. 이벤트 발행

```kotlin
fun publishOrderCreated(event: OrderCreatedEvent) {
    rabbitTemplate.convertAndSend(exchangeName, routingKey, event)
}
```

- 발행자는 이벤트를 만들고 브로커로 전달합니다.
- 학생이 기억해야 할 핵심은 **“발행자는 후속 작업을 직접 처리하지 않는다”**는 점입니다.

### 3. 이벤트 소비

```kotlin
@RabbitListener(queues = ["\${event.order.queue}"])
fun consumeOrderCreated(event: OrderCreatedEvent) {
    notificationService.record(event)
}
```

- 소비자는 이벤트를 받아 후속 작업을 수행합니다.
- 학생이 기억해야 할 핵심은 **“주문 생성과 알림 처리가 분리되었다”**는 점입니다.

## 핵심 개념 쉬운 설명

### 동기 호출

- **뜻**  
  요청한 쪽이 상대의 작업이 끝날 때까지 바로 기다리는 방식입니다.
- **왜 중요한가**  
  흐름이 단순하지만, 후속 작업이 많아질수록 호출 관계가 촘촘해질 수 있습니다.
- **이번 코드에서는 어디에 보이는가**  
  기존 CRUD, 인증 서비스 흐름 대부분이 이런 구조였습니다.

### 비동기 전달

- **뜻**  
  결과를 바로 다른 쪽에 넘기고, 발행한 쪽은 다음 작업으로 넘어갈 수 있는 방식입니다.
- **왜 중요한가**  
  후속 작업을 느슨하게 분리하기 좋습니다.
- **이번 코드에서는 어디에 보이는가**  
  `EventPublisherService`가 이벤트를 보내고, `NotificationConsumer`가 나중에 받아 처리하는 흐름에서 보입니다.

### 이벤트

- **뜻**  
  “어떤 일이 일어났다”는 사실을 담은 메시지입니다.
- **왜 중요한가**  
  발행자와 소비자가 한 메서드 안에서 강하게 묶이지 않게 도와줍니다.
- **이번 코드에서는 어디에 보이는가**  
  `OrderCreatedEvent`에서 볼 수 있습니다.

### 메시지 큐

- **뜻**  
  발행된 메시지를 전달하고 소비할 수 있게 도와주는 중간 장치입니다.
- **왜 중요한가**  
  발행자와 소비자를 직접 연결하지 않아도 흐름을 이어줄 수 있습니다.
- **이번 코드에서는 어디에 보이는가**  
  RabbitMQ와 `EventConfig`, `RabbitTemplate`, `@RabbitListener`에서 볼 수 있습니다.

### MSA 관점 소개

- **뜻**  
  MSA는 기능을 하나의 큰 애플리케이션이 아니라, 여러 서비스로 나누어 운영하는 방식입니다.
- **왜 중요한가**  
  서비스가 나뉘면 한 서비스의 결과를 다른 서비스가 알아야 하는 장면이 많아집니다.
  이때 이벤트와 메시지 큐가 연결 방식의 한 선택지가 됩니다.
- **이번 코드에서는 어디에 비유할 수 있는가**  
  지금은 하나의 애플리케이션 안에 `OrderService`, `EventPublisherService`, `NotificationConsumer`가 함께 있지만,
  그림으로 보면 `주문 서비스 -> 이벤트 큐 -> 알림 서비스`처럼 설명할 수 있습니다.
- **주의할 점**  
  이번 실습은 MSA 전체 구현이 아니라, 그 구조에서 자주 보이는 이벤트 이동 흐름만 가볍게 보는 단계입니다.

## 이번 실습에서 꼭 보면 좋은 포인트

- 이벤트에 어떤 필드만 담았는지
- 주문 생성과 알림 처리 책임이 어떻게 나뉘었는지
- 브로커는 제공되지만 학생은 발행/소비 흐름만 구현한다는 점
- 동기 호출이었다면 어디가 더 강하게 묶였을지 비교해보는 점
- 서비스를 따로 둔다고 가정했을 때 이벤트가 큐를 통해 이동하는 그림을 어떻게 설명할지 생각해보는 점

## 자주 헷갈리는 포인트

- 이벤트를 쓴다고 해서 자동으로 더 좋은 구조가 되는 것은 아닙니다.
- 이번 실습은 Kafka 운영 전체가 아니라 흐름 이해가 목표입니다.
- MSA나 메시지 큐는 무조건 답이 아니라, 시스템 규모와 문제에 따라 쓰는 선택지입니다.
- 이벤트 소비자에서 주문 생성 로직까지 다시 처리하면 책임 분리의 의미가 약해집니다.
